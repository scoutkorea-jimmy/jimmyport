# 규칙 ③ — 코드 작업·리팩터링 원칙
*(신설 2026-07-15, 사용자 가이드라인 전문 지시. 이 규칙은 기본 동작을 **오버라이드**한다.)*

우선순위: **① 기존 기능·UX를 깨뜨리지 않는다 ② 실행 흐름·의존관계를 먼저 파악한다 ③ 스파게티 구조를 그대로 복제·확장하지 않는다 ④ 변경 범위를 작고 명확하게 ⑤ 새 코드는 독립적으로 이해·테스트 가능하게 ⑥ 한 번에 다 고치지 말고 점진적으로 ⑦ 수정 전후 동작 동일성 검증.**

- **분석 먼저**: 시작/종료점·호출관계·데이터 흐름·전역 상태·외부 의존·중복·영향 범위·오류 처리·하드코딩을 확인한 뒤 착수. 추측 금지, 일부만 보고 전체 구조 단정 금지, 없는 함수/API 가정 금지.
- **기존 코드 우회**: 기존 함수에 기능을 계속 얹지 말고 **새 기능은 별도 함수/모듈**로. 위험하면 Adapter/Wrapper/Facade/Service/Utility 계층으로 우회하고 **호출부엔 최소 연결만**.
- **새 코드 기준**: 함수 1개=책임 1개 · 이름으로 목적이 드러나게(process/handleData/doWork/temp 금지) · 입력→검증→변환→처리→반환 · 전역 상태 최소화 · early return 으로 중첩 2~3단계 이내 · 숨은 부작용 금지(조회 함수가 저장하지 않기) · Boolean 매개변수로 동작 전환 금지.
- **오류**: 빈 catch 로 숨기지 않기, 전부 일반 오류로 뭉개지 않기, 민감정보 로그 금지, 부분 실패 시 불완전 저장 방지.
- **주석**: 무엇을 하는지 반복 설명 말고 **왜 이 구조인지·외부 제약·호환성 이유·임시 우회의 제거 조건**을 남긴다. 낡은 주석·주석 처리된 죽은 코드는 제거.
- **하드코딩 금지**: 상태값·URL·경로·타임아웃·권한/역할명·기준값·반복 문구는 상수/설정으로. 단 1회성 자명한 값까지 추상화하지 않기.
- **과잉 설계 금지**: 불필요한 패턴·계층·추상화·미래 대비 구현 금지. 가장 단순하면서 책임이 명확한 구조.
- **금지**: 무관한 코드 대규모 정리·스타일/파일이동/변수명 일괄변경을 기능 수정과 섞기, 테스트 없는 전면 리팩터링, 전역 변수로 임시 해결.
- **보고 형식**: ① 현재 구조 분석 ② 작업 전략(직접수정/우회/점진 분리와 이유) ③ 변경 내용(추가·수정·제거·유지) ④ 검증 내용(실행 테스트·시나리오·회귀 가능성·미확인 부분) ⑤ 남은 기술 부채(+우선순위·안전한 개선법).

⚠️ 이 repo 현황: `jamboree-plan/app.js` 는 이미 3,000줄+ 단일 파일에 전역 `state`/`Auth`/렌더러가 얽힌 구조다. **기존 관행을 이유로 복제하지 말 것** — 신규는 분리해서 붙이고, **남은 기술 부채는 해당 서비스의 `docs/<service>/changelog.md` 에 기록**한다.
